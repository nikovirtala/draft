# Start the agent's process without the person's credentials

## Context
The agent's process runs as the person's operating-system user, so it reaches whatever that user's tools reach. Found on 2026-11-22 (issue xh46a2ks): the Kiro agent ran `gh auth status` as the person, with the repo and workflow scopes, and offered to rebase-merge a pull request itself. The person's Kiro rules allow everything on purpose, so nothing stopped it. That goes around acceptance: ADR wkcnp3zr says draft writes to GitHub only as the person, from a UI action, and ADR 06wp7907 can only make the agent ask, not make the person's other tools unavailable to it.

What was found, for the options below:

- **Kiro's own sign-in** is a file under HOME: `~/Library/Application Support/kiro-cli/data.sqlite3` on macOS (table `auth_kv`), `~/.local/share/kiro-cli/data.sqlite3` on Linux ([a user's investigation of kiro-cli 2.5.1 on macOS](https://github.com/kirodotdev/Kiro/issues/9103), [Docker Sandboxes' Kiro page via collabnix](https://collabnix.com/run-kiro-docker-sandboxes-device-flow-login/)). One report says it also uses the login keychain on macOS ([Kiro issue 3963](https://github.com/kirodotdev/Kiro/issues/3963)); the other found no keychain entry. Either way it is found through HOME and `KIRO_*`/`XDG_*` variables, and it carries no GitHub or AWS credential. Kiro 3.5 also takes `KIRO_HOME` and `KIRO_API_KEY`, which are Kiro's own. HOME must not change.
- **gh** reads `GH_TOKEN`, `GITHUB_TOKEN` (github.com) and `GH_ENTERPRISE_TOKEN` before any stored credential ([gh environment](https://cli.github.com/manual/gh_help_environment)). An empty `GH_CONFIG_DIR` is not enough: when hosts.yml names no user, gh's `ActiveToken` falls back to the keychain entry stored without a user name, and gh keeps that entry set to the active token ([cli/cli internal/config/config.go](https://github.com/cli/cli/blob/trunk/internal/config/config.go): `ActiveToken`, `TokenFromKeyring`, `setActiveCredential`). So on a Mac with `gh auth login` done, an empty config folder still finds the token.
- **git** reads the system config, the global config, then the repository's own, then `GIT_CONFIG_COUNT` variables, which win over all of them. `GIT_CONFIG_NOSYSTEM` drops the system file (where Xcode's and Homebrew's gitconfig set osxkeychain), and `GIT_CONFIG_GLOBAL` replaces `$HOME/.gitconfig` and `$XDG_CONFIG_HOME/git/config` ([git](https://git-scm.com/docs/git)). An empty `credential.helper` resets the helper list, including a helper set in the repository's own config (checked with `git credential fill` against a repository with a helper of its own).
- **ssh** takes no setting from the environment for its keys or its configuration file, and finds the person's home from the password database, not HOME. `-F /dev/null` ignores the user's and the system's configuration, `IdentityFile none` loads no key, `IdentityAgent none` no agent, and `PubkeyAuthentication no` no public-key authentication ([ssh_config](https://man.openbsd.org/ssh_config)). `$GIT_SSH_COMMAND` beats `core.sshCommand` and `$GIT_SSH`.
- **aws** reads `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` from the environment, so empty files leave no profile and no SSO session to resolve ([AWS CLI environment variables](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-envvars.html)). npm reads its user config from `NPM_CONFIG_USERCONFIG` ([npm config](https://docs.npmjs.com/cli/using-npm/config)).
- **Kiro's local command sandbox** (Seatbelt on macOS, off by default) is switched on only through `sandbox.json`, at `$KIRO_HOME/settings` or `~/.kiro/settings` globally and `<workspace>/.kiro/settings` per project, or with `/sandbox` in the CLI ([Kiro: local command sandbox](https://kiro.dev/docs/sandbox), [CLI 2.31](https://kiro.dev/changelog/cli/2-31/)). Kiro's ACP documentation lists no sandbox option for `session/new`: only `modeId`, `modelId` and `effortLevel` under `_meta.kiro` ([migrate an ACP client to CLI V3](https://kiro.dev/docs/cli/v3/acp-migration/)). It covers shell commands and stdio MCP servers, not the agent's file tools or remote MCP servers, and Kiro says it "reduces risk" without guaranteeing isolation. The docs don't say which paths it hides (`~/.aws`, `~/.ssh`, the keychain).

Options considered:

- Leave it to the person's Kiro rules: they allow everything on purpose.
- Start the agent's process with an environment in which those tools find nothing, and say so.
- Run the agent's shell in a sandbox from the start: the stronger boundary, but Kiro offers no per-session switch, and draft doesn't write the person's Kiro files.
- Run the agent as another operating-system user or in a container: a bigger change to where the agent runs (ADR 1vey5j12).

## Decision
The agent's process gets an environment without the person's credentials, and acting as the person goes through draft's own steps only (acceptance, Kiro Remote).

- **One function decides it.** `agentEnvironment(spec, person's environment, data folder)` (`apps/desktop/src/main/acp/environment.ts`) is pure and returns the agent's environment and a report, by name and never by value, of what it withheld, what it set instead and what the person passed through. Everything that decides what an agent's process sees goes through it.
- **Withheld by name:** draft's own settings, as before; GitHub (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and the like); git hosts' tokens, `GIT_ASKPASS`, `GIT_CONFIG_*`, `GIT_AUTHOR_*` and `GIT_COMMITTER_*`; `SSH_AUTH_SOCK` and its relatives; every `AWS_*` except region, output, pager, CA bundle and retry settings; npm, Yarn, Cargo, Twine and uv tokens and `NPM_CONFIG_USERCONFIG`. `ANTHROPIC_API_KEY` still reaches only an agent that requires it. PATH, HOME, locale, TERM, TMPDIR, `KIRO_*` and `XDG_*` pass. HOME is never changed.
- **Set instead:** `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` to a value GitHub refuses, and `GH_CONFIG_DIR` to an empty folder, because an empty folder alone leaves the keychain's token reachable; `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` to a file draft writes (no helper, the identity `draft agent <agent@draft.invalid>`), an empty `credential.helper` through `GIT_CONFIG_COUNT`, `GIT_TERMINAL_PROMPT=0`, and `GIT_SSH_COMMAND` with `-F /dev/null`, no identity files, no agent and no public-key authentication; `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` to empty files and `AWS_EC2_METADATA_DISABLED=true`; `NPM_CONFIG_USERCONFIG` to an empty file; and a PATH that starts with a folder holding an `ssh` stand-in that runs the next `ssh` with the same options, so `ssh` and `scp` find no key either.
- **Files.** The files these point at live in `<data>/agent-env`, one set per data folder, written atomically each time an agent's process starts and written again if they are missing or changed.
- **The person's exception.** `agents.<name>.passEnv` in `config.json` lists variables to hand that agent anyway. It never passes draft's own settings, and the agent's status says when one is used. An agent's own `env` setting is the person's configuration and wins.
- **It is said.** The agent's status shows "Your GitHub, git, SSH, AWS and npm sign-ins are withheld from the agent", with the names on demand, and the session's `agent.session_started` event carries the report.
- **Kiro's own sign-in is untouched:** nothing it needs carries a GitHub or AWS credential.
- **A sandbox is the stronger boundary.** The environment stops casual use. A process that reads the person's files or calls the keychain itself still can, and so can a command that sets its own environment. Kiro's sandbox has no per-session switch (only `sandbox.json`, which draft never writes), so draft doesn't turn it on here. A later decision covers it, with what Kiro's sandbox keeps out.

## Scope
The environment of every agent's process draft starts, and what the status and the log say about it: `apps/desktop/src/main/acp/environment.ts` and `agents.ts`, the spawn in `apps/desktop/src/main/acp/runtime.ts`, and the `agent.session_started` event in `packages/core/src/events.ts`. It does not cover draft's own process: acceptance keeps using the person's git and gh (ADR wkcnp3zr, k8af6zrg).

## Consequences
- The agent's `gh`, `git`, `ssh`, `aws` and `npm` run without the person's sign-ins, so a call that needs them fails where the person can see it. `git push`, `gh pr merge`, `aws sts get-caller-identity` and `ssh -T git@github.com` fail from the agent's shell. Public GitHub reads through gh fail too, because its token is refused.
- A Kiro MCP server that reads one of the withheld variables (for example a GitHub MCP server with a personal access token) stops working until the person adds the name to `passEnv`.
- This is not a boundary against a process that wants to get around it: it can read `~/.aws`, `~/.ssh`, `~/.npmrc` and `~/.config/gh` directly, run `/usr/bin/ssh` by its path, ask the keychain with `security`, or read a credential helper named in a repository's own config for a particular URL. The agent's own file and shell tools are still refused by draft's tool policy (ADR 06wp7907) unless the person's Kiro rules allow them.
- A sandbox for the agent's shell is the real boundary. Kiro offers none per session, so it stays a follow-up that waits for Kiro or for a decision about running the agent as another user.
- The real keychain behaviour of gh and git on macOS, and kiro-cli's sign-in with this environment, can only be checked on the person's Mac.
