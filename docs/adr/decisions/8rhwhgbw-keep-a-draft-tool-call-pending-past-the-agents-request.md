# Keep a draft tool call pending past the agent's request timeout, and have the agent call again

## Context
ADR 56v0mtga makes draft's own file and shell tools steps that ask the person inside the MCP call, so the call stays open while the person decides. The agent's MCP client gives up on a request after its own timeout. Kiro's per-call `requestTimeout` is 120 000 ms by default ([custom agent configuration reference](https://kiro.dev/docs/custom-agents/configuration-reference/)), and the MCP TypeScript SDK's is 60 000 ms (`DEFAULT_REQUEST_TIMEOUT_MSEC` in `shared/protocol.ts` of `@modelcontextprotocol/sdk` 1.32). The MCP specification says implementations SHOULD set a timeout on every request and, when it passes, send `notifications/cancelled` and stop waiting ([lifecycle: timeouts](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle#timeouts), [cancellation](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation)). With draft as it was, a person who answered after the client gave up got nothing: draft saw the hangup, did not run the call, and the agent was never told why (issue cek21z1p).

What was settled before choosing, from the documentation and the SDK source (nothing here was run against a real kiro-cli):

- **draft can't be shown to raise the timeout for its own server.** `requestTimeout` is documented only as a field of an `mcpServers` entry in a Kiro agent configuration. draft's server is handed over in `session/new`, whose documented inputs are `cwd`, `mcpServers`, `additionalDirectories` and `_meta.kiro` (`modeId`, `modelId`, `effortLevel`), with no timeout for a session-supplied server ([ACP client migration](https://kiro.dev/docs/cli/v3/acp-migration/), [ACP](https://kiro.dev/docs/cli/acp/)). Kiro documents no merge of an agent file's entry with a session's. An entry in draft's agent file would have to carry the server's port and a bearer token that is new for every session, and draft keeps no token in a file. So the option isn't taken.
- **Progress notifications can't be relied on.** The specification lets a client reset its timeout on progress (it MAY) and says it SHOULD still enforce a maximum. The TypeScript SDK resets only when the caller passes `resetTimeoutOnProgress: true` (default false) and the request carries a progress token; an issue reports that the MCP client in Claude Code (and Cowork, built on it) does neither ([anthropics/claude-code#58687](https://github.com/anthropics/claude-code/issues/58687)). Kiro's documentation says nothing about progress. A progress notification also needs a streamed (SSE) response, and draft's server answers with plain JSON. No documented client is known to benefit, so it isn't built.
- **A client may hang up without closing the connection.** The SDK sends `notifications/cancelled` and keeps going; another client may just drop the socket. draft has to treat both as "the request is gone" and neither as "the call is cancelled".
- **The shortest known timeout** is the SDK's 60 s; Kiro's is 120 s. Claude Code's own limit for an MCP tool is reported to differ between its CLI and its desktop app (anthropics/claude-code#63379), so draft assumes the SDK's for every agent that isn't Kiro.

Options considered:

- Raise the timeout in draft's Kiro agent file: not possible for a per-session server (above), and no equivalent is known for Claude.
- Send progress notifications while waiting: no client is documented to reset on them, and it needs SSE.
- Answer the agent's own `session/request_permission` only after the person decided: Kiro with an allow-all rule never asks (56v0mtga), so draft can't rely on it.
- Answer an error when the request is about to time out: the agent can't tell it from a failure, and the call still can't run when the person says yes.
- Keep the call on draft's side and answer the request before the client gives up, telling the agent to call again with the same arguments (chosen).

## Decision
A draft tool call outlives the request that brought it. draft answers a request before the agent's client gives up, says the user is still deciding, and lets the agent call again; the repeated call picks the same call up.

- **One policy, one place.** `apps/desktop/src/main/acp/call-policy.ts` holds the timings and the words. A request is held for `holdMs`: 105 s for Kiro (its 120 s timeout less a 15 s margin) and 45 s for every other agent (the SDK's 60 s less the margin). A call stays pending for `retainMs`, 30 minutes from its first request.
- **"Still deciding" is a result, not an error.** After `holdMs` the request is answered with `isError: false` and a text that says the user hasn't answered, that this is not a failure, and to call the same tool again with exactly the same arguments, and that the user is asked once and the call runs once. While a command runs, it says the call is still running. The briefing (`toolsBriefing`, `packages/core/src/agent-tools.ts`) says the same, whenever the session has a tool that asks.
- **The same call.** The same tool, the same input after `toolPolicy` has parsed it (defaults filled in, keys in any order, so the JSON-RPC id and the key order don't matter), and the same turn. A request for a call that is pending joins it: the person is not asked again and nothing runs twice. Once a request has collected the call's result, the same arguments are a new call. A request that arrives again with the same JSON-RPC id keeps getting the first request's answer, as before.
- **A request leaving ends the wait, not the call.** The client's timeout, `notifications/cancelled` for that request id and a closed connection all end only that request's wait. This replaces "a call whose agent hung up before the answer doesn't run" in 56v0mtga. A result written to a request the client had already given up on is not lost: if that request is cancelled within 10 s (`cancelGraceMs`), the next request for the same call gets the result, and nothing runs again.
- **A call runs only while a request is waiting for it.** The person's answer is kept. On yes, the step begins (`step.started`) only once a request is waiting, so a change is never made when the agent is not there to be told. When no request is waiting yet, the next one starts it and gets the result. On no, nothing runs and the next request is told the user declined. A command that has begun keeps running when its request leaves, up to its own time limit, and its result goes to the next request.
- **How a call that nobody comes back for ends.** A call ends when a request collects its result, when its turn ends or is cancelled, or `retainMs` after it began. After that a yes starts no step and runs nothing, a result nobody collected is dropped, and a command still running is stopped. A step begins only after the yes and a waiting request, so none is left open: there is no `step.started` without a `step.completed`. The step and interrupt events are unchanged, and none is added.
- **Not built:** raising the timeout and progress notifications (above). Both can be added behind `call-policy.ts` if a client is shown to honor them; the fallback stays, because it works with any client.

This refines 56v0mtga, whose "asks inside the MCP call" and "a call whose agent hung up before the answer doesn't run" no longer hold as stated.

## Scope
How long draft holds an agent's request for one of its own tools while the person decides, what the agent is told then, and when a late answer is acted on: `apps/desktop/src/main/acp/call-policy.ts`, `draft-session.ts`, `draft-server.ts`, `turn.ts` (`draftCall`) and `runtime.ts`, and the line of `toolsBriefing` in `packages/core/src/agent-tools.ts` that tells the agent to call again. It does not cover Kiro Remote's tools, which the agent runs itself, or what a tool does once it runs.

## Consequences
- A person can answer after any length of time up to `retainMs` and the call still runs, once, and the agent is told the result. After 30 minutes, or when the turn ends, an answer is not acted on.
- The agent calls again every 105 s on Kiro (45 s elsewhere) while the person decides. Each repeat costs a model round trip, so a long wait costs tokens; a 30 minute wait is about 17 repeats on Kiro. Raising the timeout or progress would remove this and is left until a client is shown to honor it.
- The step is not begun before the yes and a waiting request, so a person who says yes when the agent isn't calling gets nothing until it calls again. The prompt stays on screen until it is answered: a prompt for a call that ended can still be answered, and the answer does nothing (the step is never begun). Withdrawing it from the screen needs a signal on `confirmTool` in `conversation.ts`, which this change leaves alone.
- A command is no longer stopped when its request is dropped, only at its own time limit or when its turn ends or is cancelled.
- Safe whichever way the unknowns turn out: if a client does reset its timeout on progress, or if Kiro honors a longer limit, draft still answers at `holdMs`; if a client's timeout is shorter than `holdMs`, the request is dropped and the next one joins the call.
- What only a real Kiro shows: that Kiro's request timeout is 120 s for a server supplied in `session/new` (draft answers at 105 s, which is safe if the limit is longer and not if it is shorter than 105 s); that Kiro's model calls the tool again with the same arguments when told to; whether Kiro keeps the connection open or sends `notifications/cancelled` when it gives up; and whether Kiro treats an `isError: false` result that is not the answer as done; and whether it sends `notifications/cancelled` when it gives up. A client that gives up without a cancellation after draft wrote the result loses that result, and its next call asks again.
