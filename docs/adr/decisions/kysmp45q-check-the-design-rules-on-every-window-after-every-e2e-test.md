# Check the design rules on every window after every e2e test, reading intent from data-fill marks

## Context
On 23 November #48 filled the block in focus with moved-selected, and a selected stub with a map was purple from edge to edge. #52 reversed it. The tests that existed then checked the component that had just been fixed, so the next block to take a purple fill would have passed them: the rule "a fill appears only in these places" was held by one component's test, not across the app (spec L2). The window-never-scrolls rule had the same shape: one test in map.spec.ts, for one long conversation. Both rules are statements about everything the window can show, and the e2e specs already reach many states (a thread, a check, a map, a block window). A check can read the DOM of each of them, but a computed colour alone does not say whether a fill is meant: a pale purple behind a chip is right, behind a stub it is a bug. The check needs the intent from the markup.\n\nAlternatives considered:\n\n- **Class names.** Read the allow-list as selectors (`.chip`, `.stub`) and match them against the computed colour. A class says what an element looks like, not what it is for, and a restyled or new class slips past it; the allow-list would also duplicate styles.css.\n- **Per-spec assertions.** Each spec asserts the fills of what it shows. That is the shape that failed: the next component has no test until someone writes one, and the assertions repeat across specs.\n- **Visual diffs.** Compare screenshots with the previews. The previews are drawn separately from the app, a pixel diff cannot say which colour is allowed where, and the screenshot comment already puts them side by side for a person.\n- **A stylesheet test only.** Read styles.css for rules that set a fill. It sees rules, not elements: it cannot tell a chip from a block that carries the same class, and cannot see state the app sets in script. It stays for what the e2e check cannot reach, a pointer over something (`:hover`), the one focus ring and the reduced-motion block.

## Decision
The design rules that are statements about everything on screen are checked by the e2e harness, on every window an app has open, after the last step of every test (`e2e/harness.ts` runs `e2e/design-checks.ts` when a test closes the app, or when it ends with the app open). Each check reads what is drawn and fails with the element, its colour and the rule: the window never scrolls, a fill appears only where the allow-list says, keyboard focus is one 1.5px ring and a click shows none.\n\nThe intent is in the markup. Every element that carries a fill has `data-fill="<place>"` (chosen, action, pointer, chip, cell, notice, ask; two places separated by a space). The allow-list is one table of places and the fill tokens each allows, `apps/desktop/src/shared/fills.ts`, and `test/design-fills.test.ts` fails when it differs from the table in the spec's A1. A fill token that is drawn on an element without a mark that allows it fails the test that drew it.\n\nWhat a test cannot reach is read from the stylesheet by unit tests (`test/design-fills.test.ts` for `:hover`, `test/design-focus.test.ts`, `test/design-motion.test.ts`). A rule has one check, so a narrower test of the same rule is not added.

## Scope
apps/desktop/e2e/design-checks.ts and design-page.ts, the end of apps/desktop/e2e/harness.ts, apps/desktop/src/shared/fills.ts, apps/desktop/test/design-*.test.ts, the `data-fill` attributes in apps/desktop/src/renderer/src/components, and the design rules they hold in docs/design/draft-design-spec.md.

## Consequences
Every element that carries a fill needs a mark, and a new kind of fill needs a place in the table, in the spec and in the check, in one change; forgetting the mark fails the first e2e test that shows the element, and the failure says which element and which places would allow it. The check is only as complete as the states the specs reach: a state no spec puts the app in is not checked, so a new part needs a spec that shows it. A mark is a claim, and the check does not read whether the place suits the element, only whether the place allows the colour; review still judges that. The checks add to every e2e test the time of a Tab walk through each window, and a flaky one would fail unrelated tests, so they read only what is quiet: the pointer is parked, a window is read after the test's last step. Chromium draws a 1.5px outline as 1px at 1x, so the focus check accepts 1px to 1.5px and the stylesheet test pins the declared 1.5px. A text field, a select and a separator are not pressed by the mouse check, as the platform shows `:focus-visible` on fields for any focus and a press on a separator drags it.
