# Run the agent without built-in tools that change things, and give it draft's own as steps

## Context
ADR 06wp7907 makes every agent ask with `session/request_permission` and logs a call that didn't as `agent.anomaly`. ADR 1vey5j12 starts a context's agent in the folder its person trusted and keeps draft's tool policy as it was, so the agent's own file and shell tools are refused. Both depend on the agent asking. Found on 2026-11-22 (issues aefrmdf4 and 562p472b): with a user-wide `capability: all` allow rule in `~/.kiro/settings/permissions.yaml`, which Niko chose on purpose, kiro-cli 3.5.0 never sends a permission request. Its write and shell tools run, and draft sees them only afterwards as a call without asking. A plain read raised six of those in one review. draft's instructions say the agent has no shell, Kiro gives it one, and whether it uses it depends on whether it follows the instructions that turn.

What was found, from the documentation read on 2026-11-22 and the code (nothing here was run against a real kiro-cli; see the consequences):

- **A rule can't bring back a tool the agent doesn't have.** In a Kiro agent configuration "the tools field decides which tools the agent can see and call; the permissions field decides what those tools may do when called", and rules combine with deny over ask over allow ([configuration reference](https://kiro.dev/docs/custom-agents/configuration-reference/), [permissions](https://kiro.dev/docs/permissions/)). A `tools` list without write and shell leaves them out whatever a user-wide allow says.
- **Where Kiro finds an agent, and how draft picks one.** CLI V3 reads agents from `~/.kiro/agents`, from `.kiro/agents` of a trusted workspace and from `$KIRO_HOME/agents` ([custom agents](https://kiro.dev/docs/custom-agents/), [settings reference](https://kiro.dev/docs/reference/settings/)). `kiro-cli acp` in V3 rejects `--agent`; a client picks the agent mode in `session/new` with `_meta.kiro.modeId` ([ACP client migration](https://kiro.dev/docs/cli/v3/acp-migration/), [ACP](https://kiro.dev/docs/cli/acp/)). Kiro documents no way to hand an agent over in `session/new` or to name an agent file by path.
- **KIRO_HOME moves more than agents.** In V3 it "overrides the global Kiro directory for configuration, sign-ins, sessions, and agent state" ([settings reference](https://kiro.dev/docs/reference/settings/)). The person's permission rules, MCP servers, steering and skills don't reach a session that runs with another KIRO_HOME, and Kiro has to be signed in there once.
- **Kiro's built-in calls carry no structured identity.** Only MCP tools carry one (`_meta.kiro.mcpTool`), and Kiro's own guide says never to derive a built-in tool's identity from its title ([ACP client migration](https://kiro.dev/docs/cli/v3/acp-migration/)). The "Tool Load" rule of 06wp7907 stays (issue 562p472b).
- **Claude.** `_meta.claudeCode.options` in `session/new` already carries `tools: []`. A bare tool name in `disallowedTools` removes the tool from the model's context, and a deny rule holds in every permission mode, `bypassPermissions` included ([Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions#allow-and-deny-rules), [options](https://code.claude.com/docs/en/agent-sdk/typescript)).
- **An agent's own permission request is not a gate draft controls.** Whether it asks before an MCP call depends on rules draft doesn't own. A call that reaches draft's own MCP server is the one place that holds whatever those rules say.

Options considered:

- Keep asking through `session/request_permission` and tell the agent harder not to use its shell: the agent still has the tool, and the person's rule still lets it run.
- Write draft's agent in `~/.kiro/agents` or the project's `.kiro/agents`: it edits the person's Kiro files, and a project's agents load only in a trusted workspace. Excluded by the rule that draft writes nothing under `~/.kiro` (1vey5j12).
- Run Kiro with a KIRO_HOME of draft's, holding draft's agent: no file of the person's is touched, and the agent has no built-in tool. The cost is that Kiro's configuration and sign-in are draft's own folder's.
- Take away only the built-in write and shell tools, keep Kiro's read tools: needs the same agent file, and Kiro's read tools follow symlinks out of the folder, which draft's own don't.
- Run the agent as another operating-system user or in a container: a bigger change to where the agent runs; see ADR zan5vjwz.

## Decision
draft's sessions run the agent without any built-in tool that changes things, and in a trusted folder give it draft's own file and shell tools, served by draft's MCP server, and every one of those that changes something is a step.

- **No built-in tool.** Kiro starts with an agent draft owns: `tools: ["@mcp"]`, `includeMcpJson: false`, deny rules for `fs_write`, `shell` and `subagent`. draft writes it in `<data>/kiro-home/agents/` and starts Kiro with `KIRO_HOME` set to `<data>/kiro-home`, and picks it with `_meta.kiro.modeId`. Its name is `draft-` and 16 random hex digits kept in that folder, because Kiro reads a project's own `.kiro/agents` over ACP and a project's agent of the same name would win. If the session doesn't report that agent as the one in use, draft doesn't start it. Claude keeps `settingSources: []` and `tools: []` and also denies Bash, the file-writing tools, Agent and the web tools by name. An agent of no known kind gets none of draft's tools, because draft can't take its own away.
- **draft's tools.** One registry (`read_file`, `list_files`, `search_files`, `write_file`, `edit_file`, `run_command`) and one pure policy function `toolPolicy(tool, input, context)` that returns read, change or refused (`packages/core/src/agent-tools.ts`). Everything is confined to the real path of the trusted folder, symlinks included. Writes under `.git`, `.kiro`, `.claude` and `.vscode` are refused. A command is a read only if it is one plain command from an allowlist of programs and git subcommands kept in that file, with every path argument inside the folder; every other command is a change. A new tool adds an entry and never a second path.
- **Gated by draft, not by the agent.** draft's MCP server listens on 127.0.0.1 with one bearer token per session and applies the policy itself. A read runs and is logged. A change asks the person through the interrupt every step uses, begins the durable step, runs only on yes, and settles it with the exit code, an excerpt of the output and the files changed. The agent's own permission request for one of these calls is answered with the one-time allow, so the person is asked once, by draft. A request that arrives again with the same JSON-RPC id, tool and input within a turn gets the first result and runs nothing twice. A call whose agent hung up before the answer doesn't run.
- **Told exactly.** The instructions are derived from the same registry: the tools the session offers and that changes ask, or that there are none. A context without a trusted folder offers none and says so. A built-in call that still changes something without a permission request stays a call without asking, and the instructions say why that is wrong.
- **Commands run** with the agent's environment (ADR zan5vjwz), in the folder, with a time limit, through `sh`.

This refines 06wp7907 (a call that skips the request is still an anomaly; the agent's own tools that change things are now taken away, not only asked about) and 1vey5j12 (in a trusted folder the agent has file and shell tools now, as steps).

**Not decided here.** Whether the person's Kiro rules and a folder's `.kiro` configuration should reach draft's sessions (issue mw44padb), and a sandbox for the agent's shell (zan5vjwz).

## Scope
What tools the agent has in a session, how they are policed and told: `packages/core/src/agent-tools.ts`, `packages/core/src/agent-context.ts` (the briefing), `apps/desktop/src/main/acp/` (`tools.ts`, `turn.ts`, `runtime.ts`, `draft-server.ts`, `draft-session.ts`, `folder-tools.ts`, `kiro-agent.ts`, `environment.ts`) and `apps/desktop/src/main/services.ts`.

## Consequences
- With a user-wide allow-all rule in Kiro, draft's write, edit and command steps still ask, and Kiro's own write and shell tools aren't offered, so a write or a command can't happen without the person's answer. A call that does is still shown as a call without asking.
- Kiro in draft is signed in on its own: `KIRO_HOME=<data>/kiro-home kiro-cli login` once. The person's Kiro rules, MCP servers, steering and skills don't apply in draft's sessions until issue mw44padb decides what to show and allow. A person who set `agents.kiro.env.KIRO_HOME` gets a session that doesn't start, with the reason.
- The agent has no built-in read tools either. draft's reads follow the same confinement, and a search is plain text, not a regular expression, so a pattern can't stall draft's process; `rg` is an allowlisted command.
- A call that changes something asks inside the MCP call, so Kiro's per-call MCP timeout (`requestTimeout`, 120 s by default) can end it before the person answers. The call then doesn't run and the step shows as failed. A way around it (progress notifications, or the agent's permission request) is left for later.
- The step's input holds a preview of a file's content and a SHA-256, not the whole content. The files a command changed come from git's view of the folder, so a folder that isn't a git repository says they are unknown.
- A read-only command can still run a program a repository's own git configuration names (for example a textconv filter or `core.fsmonitor`). The folder is the one the person trusted. Commands that need an executable path, a pipe or a redirect ask.
- The agent can read any file in the folder without asking, `.env` files included, and its model provider receives what it reads.
- `sh` and `/bin/sh` mean macOS and Linux. Windows has no file or shell tools until someone decides what they run.
- What only a real Kiro shows: that `_meta.kiro.modeId` selects the agent, that its `tools` list leaves every built-in out when session-supplied MCP servers are matched by `@mcp`, that the session reports it as the agent in use, that the MCP tool call carries `_meta.kiro.mcpTool` so draft's own calls aren't reported as calls without asking, and the MCP timeout. draft doesn't start a session in which the agent isn't reported.
